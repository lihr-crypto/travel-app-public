# Web 协作与可携带行程：建议方案

状态：用户于2026-10-13明确批准实施三阶段方案，现已完成。网页版共同编辑、Safari／主屏幕同步、离线重连、跨账号文件导入、副本修改独立性和撤权通过真人验收。版本11同字段冲突保护通过本机浏览器／SQL检查。原 App最终补装、文件选择／导入／重开、已有副本更新／恢复及仅到达时间通过真人操作和新数据库备份核验，全部原有记录保持不变。用户另行批准向指定邮箱添加站点访客并接受可能自动发送的邀请邮件。旧备份仍不自动上传。

## 用户可观察的行为

1. 自己拥有一趟旅行，邀请朋友编辑同一份计划。只有获授权的成员可查看；保存后其他成员数秒内看到更新。
2. 导出一趟旅行文件，别人导入后成为他主页里的独立旅行。修改副本不回写共享原件。
3. 同一文件能导入原iPhone App，保留日期、排序、名称、时间、备注、交通/住宿字段与地点来源/坐标。
4. 同一账号在Safari和主屏幕读取同一份云端行程；本机副本支持离线。离线待同步不能冒充已保存到云端。

## 方案提出时的代码事实与手机证据（历史基线）

- Web目前使用IndexedDB快照、原Application Commands；服务器只有界面资源、地图配置/代理，没有行程数据库。
- 已有整库JSON导出/导入、SHA-256校验、默认保留当前重复数据以及恢复记录。没有单趟可携带复制协议。
- 原生src/未发现文件导入、DocumentPicker或行程备份入口。需要补导入Command、校验/预览及一次App更新。
- 手机用户确认：主屏幕中新建旅行能够保留，Safari创建的旅行不出现在主屏幕。
  WebKit说明Safari与安装后的Web App不共享网站数据；这是两份存储，不是主屏幕写入失效。
- 当前Sites仅有一个Owner；支持受邀请的外部访客。朋友当前没有访问权限。站点访问角色与行程编辑角色必须分开，不能给朋友代码编辑权限来代替协作权限。

## 推荐结构

- 云端为共享行程主数据，本机为缓存/离线工作副本。继续复用现有Trip → Day → Ordered Items及Provider/CRS规则。
- 初版沿用已选托管及其身份能力，服务端以可信用户ID授权。面向朋友的正式登录方式需结合他们能否使用当前账号/网络环境确认。
- 当前托管支持D1结构化数据。Trip与成员权限独立保存，所有查询/写入在服务器验证成员与角色。
- 先做保存操作级的近实时同步。不要直接用最后上传的整个快照覆盖他人修改。
- 每次命令带版本/幂等操作ID。不同项目可合并；同一字段、排序、日期增删发生冲突时保留双方内容并要求处理。
- 离线变更与本机副本原子记录，联网再提交。权限失效或版本冲突不能静默丢弃离线改动。
- 本机缓存绑定用户身份；服务器不会因客户端提交一个Owner ID就授予访问。
- Owner管理成员、删除整趟旅行/恢复版本；Editor编辑条目与安排；Viewer只读。可撤销邀请。

## 文件互通

- 统一单趟格式 travel-trip-package / schemaVersion1，包含该Trip、Days、Items、所引用Places与校验信息。
- 不含其他旅行、个人完整原始表档案、地图Key、账号凭据或共享编辑权限。
- 默认导入为新副本：重建内部Trip/Day/Item/Place ID及引用，保留内容/顺序/源坐标；保留导入来源以便辨识。
- 更新已有同源旅行作为显式选项，先比较差异、保留恢复点；不按名称猜测覆盖。
- 原App先支持文件快照导入。原App与云端实时同步是另一个范围，不从“导入”推定。
- 历史混合来源保留原名称/坐标/记录，不强制转换或丢弃。新旅行仍固定大陆/海外。

## 推进顺序与验收

1. 账号/权限、云端存储与同步：两个账号协作同一Trip；不同Trip隔离；并发/撤权/离线重连不丢数据；Safari/主屏幕一致。
2. 单趟导出/网页导入：他人导入产生独立副本；多次导入有明确重复策略；坏文件不改变原计划；包不包含密钥或无关旅行。
3. 原App导入：导入预览、备份恢复、SQLite原子写入与来源校验；在真机上验证已有数据不受影响。

三阶段实施及指定访客访问已获授权。Agent开发／验收使用公共测试样例；不自动上传当前旧备份，不自动给任何朋友发消息或追加邀请。
